## 한 것 (3단계)

| 단계 | 요구사항 | 겪은 것 |
|---|---|---|
| 1 | VIP 는 1,000원 고정 할인. 가장 단순하게 | `OrderService` 안에서 `FixDiscountPolicy()` 를 직접 만들어 씀 |
| 2 | 기획 변경: VIP 는 가격의 10% | 정책이 바뀌었는데 `OrderService.kt` 를 열어 고쳐야 했다 |
| 3 | `OrderService` 를 안 고치고 정책을 바꿔 끼우기 | 인터페이스를 만들고 생성자로 받게 바꿈. 테스트 2개 통과 |

### 3단계에서 돌아간 길
처음에는 `enum DiscountType` 을 넘기고 `OrderService` 에서 `when` 으로 분기하려 했다.
이 방식은 정책이 하나 추가될 때마다 `enum` 과 `OrderService` 의 `when` 을 또 고쳐야 한다.
2단계의 불편이 그대로 남고 가지만 늘어난다.

Python 으로 보면 차이가 분명하다.

```python
# 종류를 넘기고 분기
def create_order(grade, price, discount_type):
    if discount_type == "rate":
        discount = RatePolicy().discount(grade, price)
    elif discount_type == "fixed":
        discount = FixPolicy().discount(grade, price)
    return Order(price, discount)

# 객체를 넘긴다. 분기가 없다
def create_order(grade, price, policy):
    return Order(price, policy.discount(grade, price))
```

분기는 없어진 게 아니라 "어떤 객체를 넘길지 고르는 쪽"으로 옮겨 간다.

## 최종 코드

```kotlin
interface DiscountPolicy {
    fun discount(grade: Grade, price: Int): Int
}

class FixDiscountPolicy : DiscountPolicy {
    override fun discount(grade: Grade, price: Int): Int {
        when (grade) {
            Grade.BASIC -> return 0
            Grade.VIP -> return 1000
        }
    }
}

class OrderService(val discountPolicy: DiscountPolicy) {
    fun createOrder(grade: Grade, price: Int): Order {
        val discountPrice: Int = discountPolicy.discount(grade, price)
        val order: Order = Order(price, discountPrice)
        return order
    }
}
```

```kotlin
@Test
fun rateDiscount() {
    val orderService = OrderService(RateDiscountPolicy())
    val order = orderService.createOrder(Grade.VIP, 200_000)
    Assertions.assertThat(order.discountPrice).isEqualTo(20000)
}
```

## DI 정리

- **의존**: `OrderService` 는 할인 정책이 있어야 일을 할 수 있다. 이때 `OrderService` 가 할인 정책에 의존한다고 말한다.
- **의존성 주입(DI)**: 필요한 객체를 스스로 만들지 않고, 밖에서 넣어 주는 것을 받아 쓴다.
- **제어의 역전(IoC)**: 무엇을 쓸지 정하는 권한이 `OrderService` 에서 바깥으로 넘어간다.

| | 직접 만든다 (2단계) | 밖에서 받는다 (3단계) |
|---|---|---|
| `OrderService` 가 아는 것 | 할인 정책이 필요하다 + 그게 `RateDiscountPolicy` 다 | 할인 정책이 필요하다 |
| 정책을 바꾸려면 | `OrderService` 를 고친다 | 넣는 객체만 바꾼다 |
| 테스트 | 정책을 바꿔 끼울 수 없다 | 테스트마다 원하는 정책을 넣는다 |

### 겪은 것에 이름 붙이기

| 겪은 것 | 이름 |
|---|---|
| 정책이 바뀌었는데 `OrderService` 를 고쳐야 했다 | OCP 위반. 기능을 추가할 때 기존 코드는 안 고쳐야 한다 |
| `OrderService` 가 구체 클래스 이름을 직접 알았다 | DIP 위반. 구체 클래스가 아니라 인터페이스에 의존해야 한다 |
| 정책을 만들 때 밖에서 받게 했다 | 의존성 주입, 그중 생성자 주입 |

### DI 가 성립하려면
1. 인터페이스에 의존해야 한다. 구체 클래스 타입으로 받으면 다른 구현을 못 넣는다.
2. 넣어 주는 누군가가 있어야 한다. 지금은 테스트가 넣어 준다. 스프링에서는 컨테이너가 한다 (다음 회차).

### Django 와 다른 점
Django 에서는 함수 안에서 `import` 한 것을 바로 쓴다. 테스트에서 바꿔 끼우려면 `mock.patch` 로 덮어쓴다.
DI 에서는 덮어쓰지 않고 다른 객체를 넣는다.

## 틀린 것

| 틀린 것 | 맞는 것 | 메모 |
|---|---|---|
| `fun f(...) -> Int` | `fun f(...): Int` | Python 표기. 또 나왔다 |
| 클래스 없이 함수만 작성 | `class FixDiscountPolicy { fun discount(...) }` | 바꿔 끼우려면 객체여야 한다 |
| `if / else if` 로 끝내고 `else` 없음 | `when (grade) { ... }` | 컴파일러는 두 조건이 모든 경우를 덮는지 모른다 |
| `when` 에 `else` 가지 | enum 값을 전부 나열 | `else` 를 쓰면 등급이 추가돼도 컴파일러가 못 잡는다 |
| `when` 가지에서 값을 계산만 함 | 가지마다 `return`, 또는 `return when (...) { ... }` | 식으로 쓰면 `return` 은 한 번 |
| `class Policy(val grade, val price)` | `fun discount(grade, price)` | 정책은 규칙이고 등급·가격은 매번 바뀌는 입력이다 |
| `return price - discountPrice` | `return discountPrice` | 요구사항은 "할인 금액"이었다 |
| `price * 10`, BASIC 은 `price` | 10% 계산, BASIC 은 `0` | 컴파일러가 못 잡는 종류. 테스트가 잡는다 |
| `import org.junit.jupiter.api.Assertions` | `import org.assertj.core.api.Assertions` | 이름이 같은 클래스가 두 라이브러리에 있다. `assertThat` 은 AssertJ |
| `Assertions.assertThat(order)` | `assertThat(order.discountPrice).isEqualTo(1000)` | 집어 들기만 하고 확인을 안 했다 |
| `createOrder(val discountPolicy: ...)` | `class OrderService(val discountPolicy: ...)` | `val` 은 함수 입력에 못 붙인다. 주 생성자에서 쓴다 |

## 남긴 것
- `OrderService(val discountPolicy)` → `private val` 로. 지금은 밖에서 꺼낼 수 있다.
- `(price * 0.1).toInt()` → 금액은 정수끼리만 계산한다.
