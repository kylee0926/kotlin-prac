# 2026-11-24 핵심 원리 드릴 2회차 — 스프링 컨테이너가 뭐고 왜 쓰나

강의 없이, 요구사항을 받아 Kotlin 으로 직접 짜는 방식.
코드: `hello-spring` 레포의 `hello.core` 패키지.

## 오늘 답할 수 있어야 하는 질문
- 스프링 컨테이너가 뭐고, 왜 쓰나요? 객체를 직접 만들어 넘기면 안 되나요?

## 소요 시간
- 미기록

## 한 것 (3단계)

| 단계 | 요구사항 | 겪은 것 |
|---|---|---|
| 1 | 조립을 한 곳으로 모으기 (스프링 없이) | `AppConfig` 를 만들었다. 테스트에서 정책 클래스 이름이 사라졌다 |
| 2 | 그 조립을 스프링 컨테이너에 맡기기 | `@Configuration`, `@Bean` 을 붙이고 컨테이너에서 꺼내 썼다 |
| 3 | 컨테이너 안을 들여다보기 | 빈 이름 목록을 출력했고, 같은 타입의 빈이 둘일 때의 오류를 직접 봤다 |

### "누가 정책을 정하나"가 옮겨 간 흐름

| 시점 | 정책 클래스 이름을 아는 곳 | 조립하는 곳 | 남은 문제 |
|---|---|---|---|
| 1회차 처음 | `OrderService` 안 | `OrderService` 안 | 정책을 바꾸려면 `OrderService` 를 고쳐야 한다 |
| 1회차 끝 | `OrderService` 를 쓰는 곳 | 쓰는 곳 | 쓰는 곳이 50군데면 50군데를 고쳐야 한다 |
| 2회차 1단계 | `AppConfig` 한 곳 | `AppConfig`. 내가 만들고 메서드를 부른다 | 쓰는 곳마다 `AppConfig()` 를 만들어 불러야 한다 |
| 2회차 2단계 | `AppConfig` 한 곳 | 스프링. `AppConfig` 를 읽어서 대신 부른다 | (다음 회차부터) |

### 1단계에서 돌아간 길
`AppConfig` 에서도 정책을 밖에서 받으려고 했다.

```kotlin
// 첫 시도: 메서드 인자로 받음 → 부르는 쪽이 정책을 넘겨야 한다
fun orderService(discountPolicy: DiscountPolicy): OrderService

// 둘째 시도: 생성자로 받음 → AppConfig 를 만드는 쪽이 정책을 넘겨야 한다
class AppConfig(val discountPolicy: DiscountPolicy)
```

1회차에서 배운 "필요한 건 밖에서 받는다"를 그대로 적용한 것인데, 그건 받는 쪽의 규칙이다.
받기만 해서는 끝이 안 난다. 어딘가 한 곳은 `FixDiscountPolicy()` 라고 직접 적어야 한다.

| | 정책을 밖에서 받나 | 구체 클래스 이름을 아나 |
|---|---|---|
| `OrderService` | 받는다 | 모른다 |
| `AppConfig` | 안 받는다 | 안다. 여기서만 |

그리고 테스트 두 개(`fixedDiscount`, `rateDiscount`)를 그대로 두었더니 하나가 실패했다.
둘 다 `AppConfig` 에서 받으니 같은 정책이 나온다. 테스트는 이제 정책을 고를 수 없다. 1단계가 제대로 됐다는 증거다.

## 최종 코드

```kotlin
@Configuration
class AppConfig {
    @Bean
    fun discountPolicy(): DiscountPolicy {
        return FixDiscountPolicy()
    }

    @Bean
    fun orderService(): OrderService {
        return OrderService(discountPolicy = this.discountPolicy())
    }

    @Bean
    fun rateDiscountPolicy(): DiscountPolicy {   // 3단계 실험용
        return RateDiscountPolicy()
    }
}
```

```kotlin
class OrderServiceTest {
    val ac = AnnotationConfigApplicationContext(AppConfig::class.java)

    @Test
    fun createOrder() {
        val orderService: OrderService = ac.getBean(OrderService::class.java)
        val order = orderService.createOrder(grade = Grade.VIP, 200_000)
        Assertions.assertThat(order.discountPrice).isEqualTo(1000)
    }
}
```

```kotlin
@Test
fun rateDiscountPolicy() {
    val discountPolicy = ac.getBean("rateDiscountPolicy", DiscountPolicy::class.java)
    Assertions.assertThat(discountPolicy).isInstanceOf(RateDiscountPolicy::class.java)
}
```

## 스프링 컨테이너 정리

객체를 만들어서 이름표를 붙여 보관하는 통이다. Python 으로 치면 딕셔너리 하나다.

```python
container = {}

config = AppConfig()
container["discountPolicy"] = config.discount_policy()
container["orderService"] = config.order_service()

order_service = container["orderService"]   # 쓰는 쪽은 꺼내기만 한다
```

1단계에서는 가운데 세 줄을 내가 했고, 2단계부터는 스프링이 한다.

| 애너테이션 | 스프링에게 하는 말 |
|---|---|
| `@Configuration` | 이 클래스는 설정 클래스다. 안에 객체 만드는 방법이 적혀 있다 |
| `@Bean` | 이 메서드를 스프링이 불러서, 돌려받은 객체를 통에 보관한다. 이름표는 메서드 이름 |

애너테이션은 표시일 뿐이다. 그 표시를 읽고 움직이는 쪽은 스프링이다.

### 컨테이너를 만드는 한 줄에서 일어나는 일
`AnnotationConfigApplicationContext(AppConfig::class.java)`

1. `AppConfig` 에 `@Configuration` 이 붙은 것을 확인한다
2. `@Bean` 이 붙은 메서드를 찾는다
3. 그 메서드들을 스프링이 직접 부른다
4. 돌려받은 객체를 이름표를 붙여 보관한다

`getBean(OrderService::class.java)` 는 새로 만들지 않고, 이미 만들어 둔 것을 꺼내 준다.

### 통 안을 출력해 보니 (빈 9개)

| 이름 | 누가 등록했나 |
|---|---|
| `org.springframework...` 로 시작하는 6개 | 스프링이 자기 일을 하려고 넣어 둔 것 |
| `appConfig` | 설정 클래스 자체. 이것도 빈이다 |
| `discountPolicy`, `orderService` | 내가 `@Bean` 으로 등록한 것. 이름이 메서드 이름 그대로다 |

### 같은 타입의 빈이 둘이면
`DiscountPolicy` 타입의 빈을 하나 더 등록하고 타입으로 꺼냈더니 오류가 났다.

```
NoUniqueBeanDefinitionException:
No qualifying bean of type 'hello.core.DiscountPolicy' available:
expected single matching bean but found 2: discountPolicy,rateDiscountPolicy
```

스프링은 아무거나 골라 주지 않는다. 마지막 줄에 찾던 타입, 후보 개수, 후보 이름이 나온다.

| 해결 방법 | 어떻게 |
|---|---|
| 이름으로 꺼낸다 | `getBean("rateDiscountPolicy", DiscountPolicy::class.java)` |
| 기본값을 정한다 | 둘 중 하나에 `@Primary` |
| 받는 쪽에서 지정한다 | 주입받는 자리에 `@Qualifier("이름")` |

이때 `OrderServiceTest` 는 그대로 통과했다. `orderService()` 가 타입으로 찾지 않고 `discountPolicy()` 메서드를 콕 집어 불렀기 때문이다.

### 용어

| 한 일 | 용어 |
|---|---|
| 필요한 객체를 밖에서 받는다 | 의존성 주입 (DI) |
| 내 코드를 내가 부르지 않고 프레임워크가 부른다 | 제어의 역전 (IoC) |
| 객체를 만들어 보관하는 통 | 스프링 컨테이너 (`ApplicationContext`) |
| 통에 보관된 객체 | 빈 (bean) |
| 객체 만드는 방법을 적은 클래스 | 설정 클래스 |

### Django 와 닮은 점
`INSTALLED_APPS` 에 앱을 적어 두면 Django 가 시작할 때 읽어서 등록하고, 나중에 `apps.get_model(...)` 로 꺼낸다.
"적어 둔다 → 프레임워크가 시작할 때 읽어 만든다 → 필요할 때 꺼낸다"는 흐름이 같다.

### 아직 안 보이는 것
1단계와 2단계는 결과가 같다. 이 크기의 코드에서는 컨테이너의 이득이 안 보인다.
이득은 "통에 보관해 둔 객체에 스프링이 손을 댈 수 있다"는 데서 나온다. 싱글톤(3회차), 자동 주입(4회차), `@Transactional`(6회차)이 그 위에 얹힌다.

## 틀린 것

| 틀린 것 | 맞는 것 | 메모 |
|---|---|---|
| `fun orderService(discountPolicy: DiscountPolicy)` | `fun orderService()` 안에서 `discountPolicy()` 호출 | 조립하는 곳이 정책을 밖에서 받으면 조립 책임이 다시 새어 나간다 |
| `class AppConfig(val discountPolicy: DiscountPolicy)` | `class AppConfig` (인자 없음) | 위와 같은 문제가 한 칸 옮겨 갔을 뿐이다 |
| "테스트 클래스 안에 `AppConfig` 클래스를 또 만든다" | `val appConfig = AppConfig()` | 클래스를 정의하는 것과 객체를 만드는 것은 다르다. Kotlin 은 `new` 가 없다 |
| 정책별 테스트 2개를 그대로 둠 | 테스트 1개 | 정책을 고르는 권한이 `AppConfig` 로 넘어갔다 |
| `getBean(DiscountPolicy::class.java, RateDiscountPolicy())` | `getBean("rateDiscountPolicy", DiscountPolicy::class.java)` | 이름표는 문자열이다. 이름이 앞, 타입이 뒤 |
| `"RateDiscountPolicy"` | `"rateDiscountPolicy"` | 빈 이름은 클래스 이름이 아니라 메서드 이름이다 |
| `isEqualTo(RateDiscountPolicy())` | `isInstanceOf(RateDiscountPolicy::class.java)` | 새로 만든 객체와 같은지가 아니라 그 클래스인지를 묻는다. Python 의 `isinstance` |
| `isInstanceOf(RateDiscountPolicy)` | `RateDiscountPolicy::class.java` | Kotlin 에서 클래스 이름만으로는 값이 안 된다 |

### 이번 회차의 공통 실수
클래스를 넘길 자리에 객체를 만들어 넘겼다.

| 쓴 것 | 뜻 |
|---|---|
| `RateDiscountPolicy()` | 객체를 새로 만든다 |
| `RateDiscountPolicy::class.java` | 클래스 자체를 가리킨다 |
| `RateDiscountPolicy` | 혼자서는 값으로 못 쓴다 |

## 새로 쓴 Kotlin
- `this.discountPolicy()` 의 `this` 는 생략할 수 있다. Python 의 `self.` 와 다르다.
- `for (name in 목록) { println(name) }`
- 테스트 클래스의 속성(`val ac = ...`)은 테스트 메서드마다 새로 만들어진다. JUnit 이 메서드마다 테스트 객체를 새로 만든다.
- `@BeforeEach`, `@AfterEach` 는 준비 코드가 반복되거나 치울 것이 있을 때 쓴다. 오늘은 둘 다 없었다.

## 남긴 것
- `AppConfig` 의 `rateDiscountPolicy` 빈은 3단계 실험용으로 남아 있다.
- 1회차에서 남긴 것 그대로: `OrderService(val discountPolicy)` → `private val`, 금액은 정수끼리만 계산.
