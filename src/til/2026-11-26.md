# 2026-11-26 핵심 원리 드릴 3회차 — 스프링 빈은 왜 싱글톤인가

강의 없이, 요구사항을 받아 Kotlin 으로 직접 짜는 방식.
코드: `hello-spring` 레포의 `hello.core` 패키지, `SingletonTest`.

## 오늘 답할 수 있어야 하는 질문
- 스프링 빈은 왜 기본이 싱글톤인가요? 그래서 무엇을 조심해야 하나요?

## 소요 시간
- 미기록

## 한 것 (3단계)

| 단계 | 확인한 것 | 결과 |
|---|---|---|
| 1 | 스프링 없이 `AppConfig().orderService()` 를 두 번 부르면 | 다른 객체 2개 |
| 2 | 컨테이너에서 `getBean` 을 두 번 하면 | 같은 객체 1개 |
| 3 | `orderService()` 도 `discountPolicy()` 를 부르는데 정책 객체는 몇 개인가 | 1개. `discountPolicy()` 는 한 번만 실행됐다 |

세 단계 모두 실행 전 예상이 틀렸다. 틀린 곳이 그대로 오늘 배운 것이다.

## 1단계 — 스프링 없이 부르면 부를 때마다 새로 만든다

```kotlin
@Test
fun pureContainer() {
    val appConfig: AppConfig = AppConfig()
    val orderService1: OrderService = appConfig.orderService()
    val orderService2: OrderService = appConfig.orderService()
    println(orderService1)
    println(orderService2)
    Assertions.assertThat(orderService1).isNotSameAs(orderService2)
}
```

```
hello.core.OrderService@ab20d7c
hello.core.OrderService@4f4c789f
```

`@` 뒤의 값이 다르다. `orderService()` 안의 `return OrderService(...)` 가 부를 때마다 실행되기 때문이다.
요청마다 이 메서드를 부르면 내용이 똑같은 객체를 요청 수만큼 만들고 버리게 된다.

## 2단계 — 컨테이너에서 꺼내면 항상 같은 객체다

```kotlin
@Test
fun springContainer() {
    val orderService1: OrderService = ac.getBean("orderService", OrderService::class.java)
    val orderService2: OrderService = ac.getBean("orderService", OrderService::class.java)
    println(orderService1)
    println(orderService2)
    Assertions.assertThat(orderService1).isSameAs(orderService2)
}
```

```
hello.core.OrderService@4c48fe92
hello.core.OrderService@4c48fe92
```

Python 딕셔너리로 보면 당연하다.

```python
container["orderService"] = config.order_service()   # 시작할 때 한 번 만든다

a = container["orderService"]   # 꺼내기만 한다
b = container["orderService"]
a is b   # True
```

| | `orderService()` 가 실행되는 횟수 | 객체 수 |
|---|---|---|
| `appConfig.orderService()` 두 번 | 2번 | 2개 |
| `ac.getBean(...)` 두 번 | 1번 (컨테이너를 만들 때) | 1개 |

`getBean` 은 만드는 것이 아니라 꺼내는 것이다.
객체를 하나만 만들어 계속 같이 쓰는 방식을 싱글톤(singleton)이라고 한다. 스프링 빈은 따로 지정하지 않으면 싱글톤이다.

## 3단계 — `discountPolicy()` 는 왜 한 번만 불렸나

```kotlin
@Configuration
class AppConfig {
    @Bean
    fun discountPolicy(): DiscountPolicy {
        println("call discountpolicy")
        return FixDiscountPolicy()
    }

    @Bean
    fun orderService(): OrderService {
        println("call orderService")
        return OrderService(discountPolicy = this.discountPolicy())
    }
}
```

```kotlin
@Test
fun configurationDeep() {
    println(ac.getBean(AppConfig::class.java))
}
```

```
call discountpolicy
call orderService
hello.core.AppConfig$$SpringCGLIB$$0@1abc9f14
```

| 코드만 보고 한 예상 | 실제 |
|---|---|
| `call discountpolicy` 가 2번 (스프링이 1번, `orderService()` 안에서 1번) | 1번 |
| 클래스 이름이 `hello.core.AppConfig` | `AppConfig$$SpringCGLIB$$0` |

컨테이너에 들어 있는 것은 내가 만든 `AppConfig` 가 아니다. 스프링이 `AppConfig` 를 상속해서 만든 자식 클래스다.
`CGLIB` 는 실행 중에 클래스를 만들어 내는 라이브러리 이름이다. Python 으로 쓰면 이런 클래스를 스프링이 만든 셈이다.

```python
class AppConfigProxy(AppConfig):
    def discount_policy(self):
        if "discountPolicy" in container:        # 이미 만들어 둔 것이 있으면
            return container["discountPolicy"]   # 그것을 돌려준다
        obj = super().discount_policy()          # 없을 때만 내 원래 코드를 부른다
        container["discountPolicy"] = obj
        return obj
```

`orderService()` 안의 `this.discountPolicy()` 에서 `this` 는 이 자식 객체다.
그래서 자식이 덮어쓴 메서드가 불리고, 통에 이미 있는 객체를 돌려받는다. `println` 은 내 원래 코드 안에 있으니 한 번만 찍힌다.

원래 객체 대신 끼워 넣어 호출을 가로채는 객체를 프록시(proxy)라고 한다.

비교: 1단계(스프링 없음)에서는 가로채는 것이 없어서 `orderService()` 를 부를 때마다 `discountPolicy()` 도 같이 실행됐다.

```
call orderService
call discountpolicy
call orderService
call discountpolicy
```

### 아직 안 해 본 확인
- `@Configuration` 을 지우고 `configurationDeep` 을 실행하면 `call discountpolicy` 가 2번 찍히고 클래스 이름에서 `$$SpringCGLIB$$0` 이 사라질 것으로 예상한다. 직접 돌려 보지는 않았다.

### Kotlin 에서 하나 더
상속하려면 클래스가 열려 있어야 하는데 Kotlin 클래스는 기본이 `final` 이다.
오류가 안 난 것은 `build.gradle` 의 `kotlin("plugin.spring")` 이 `@Configuration` 같은 애너테이션이 붙은 클래스를 자동으로 `open` 으로 바꿔 주기 때문이다.

## 질문에 대한 답

| | |
|---|---|
| 왜 싱글톤인가 | 서비스 객체는 요청마다 내용이 같다. 부를 때마다 만들면 같은 객체를 요청 수만큼 만들고 버린다. 하나만 만들어 같이 쓰면 그 비용이 없다 |
| 무엇을 조심하나 | 객체 하나를 모든 요청이 같이 쓰므로, 빈에 값이 바뀌는 필드를 두면 안 된다. 상태가 없어야 한다(stateless) |

```kotlin
class OrderService(...) {
    var price = 0                    // 값이 바뀌는 필드: 위험
    fun createOrder(price: Int) {
        this.price = price           // A 요청이 10000 을 넣은 직후 B 요청이 20000 을 넣으면
        ...                          // A 는 20000 으로 계산한다
    }
}
```

요청마다 다른 값은 필드가 아니라 인자와 지역 변수로 다룬다.

### Django 와 다른 점
클래스 기반 뷰는 요청마다 객체가 새로 만들어져서 `self.xxx` 에 값을 넣어도 안전하다.
스프링 빈은 하나를 같이 쓴다. Django 에서 모듈 전역 변수에 요청 값을 넣는 것과 같은 사고가 난다.

### 용어

| 한 일 | 용어 |
|---|---|
| 객체를 하나만 만들어 같이 쓴다 | 싱글톤 (singleton) |
| 빈에 값이 바뀌는 필드가 없다 | 무상태 (stateless) |
| 원래 객체 대신 끼워 넣어 호출을 가로채는 객체 | 프록시 (proxy) |
| 실행 중에 자식 클래스를 만들어 내는 라이브러리 | CGLIB |

## 틀린 것

| 틀린 것 | 맞는 것 | 메모 |
|---|---|---|
| 테스트 메서드에 `@Test` 를 안 붙임 | `@Test fun pureContainer()` | `No tests found` 는 코드가 틀린 것이 아니라 JUnit 이 테스트를 못 찾았다는 뜻이다 |
| 1단계 `isSameAs` | `isNotSameAs` | 같은 메서드를 불렀으니 같은 객체라고 생각했다. 메서드는 부를 때마다 실행된다 |
| `getBean("createOrder", ...)` | `getBean("orderService", ...)` | 빈 이름은 `AppConfig` 에서 `@Bean` 이 붙은 메서드의 이름이다. `createOrder` 는 `OrderService` 의 기능 메서드다 |
| 2단계 `isNotSameAs` | `isSameAs` | `getBean` 을 "만든다"로 읽었다. 꺼내는 것이다 |
| `return ac.getBean(this::class.java)` | `println(ac.getBean(AppConfig::class.java))` | `this` 는 테스트 객체라서 `this::class.java` 는 `SingletonTest` 다. 테스트 메서드는 값을 돌려주지 않는다 |
| 실행 전 예상을 주석으로 안 적음 | 예상 한 줄을 먼저 적는다 | 예상을 적어 두어야 틀렸을 때 왜 틀렸는지가 남는다 |

### 지난 회차에 이어 또 나온 실수
클래스를 가리킬 자리에서 다른 것을 썼다.

| 쓴 것 | 뜻 |
|---|---|
| `this::class.java` | 지금 이 코드가 들어 있는 클래스. Python 의 `type(self)` |
| `AppConfig::class.java` | `AppConfig` 클래스 |

## 새로 쓴 Kotlin / AssertJ
- `isSameAs`, `isNotSameAs`: 같은 객체인지 묻는다. Python 의 `is`. `isEqualTo` 는 `==` 에 해당한다.
- 객체를 `println` 하면 `패키지.클래스@해시값` 이 나온다. `@` 뒤를 보면 같은 객체인지 눈으로 알 수 있다.
- 테스트 메서드 하나만 실행: `./gradlew test --tests "hello.core.SingletonTest.configurationDeep"`

## 남긴 것
- `AppConfig` 에 `println` 두 줄이 남아 있다. 다음 회차를 시작할 때 지운다.
- `AppConfig` 의 `rateDiscountPolicy` 빈은 2회차 실험용으로 남아 있다.

## 공식 문서 위치
- Spring Framework 레퍼런스 → Core Technologies → The IoC Container
  - Bean Scopes (싱글톤이 기본이라는 것)
  - Java-based Container Configuration → `@Configuration` 클래스 안에서 `@Bean` 메서드끼리 부를 때의 동작
